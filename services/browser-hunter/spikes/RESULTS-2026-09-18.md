# Spike results — 2026-09-18

**Executed for real this time.** The user supplied `TYPESAFE_API_KEY` (found in the
environment under the name `TYPESAFE`, not `TYPESAFE_API_KEY` — the library reads it via
`os.environ["TYPESAFE_API_KEY"]` verbatim, so it had to be re-exported under the exact name).
`TEXT_MODEL_API_KEY` was pointed at the existing `OPENROUTER_API_KEY` via
`TEXT_MODEL_BASE_URL=https://openrouter.ai/api/v1`, `TEXT_MODEL=deepseek/deepseek-v4-pro-0813`,
per the deep-dive's own recommendation — no separate DeepSeek key was needed.

## What had to be built to run it at all

`jev-ultrafast` isn't on PyPI; installed from source (cloned at commit `452c1ad`) into a
Python 3.12 venv (this environment's default `python3` is 3.11, below the library's stated
minimum). Its dependency `browser-harness` expects an **already-running** Chrome with a
remote-debugging port open — it does not launch one from a binary path on its own, contrary
to what the original proposal assumed. Launched the environment's bundled Playwright
Chromium headlessly (`--remote-debugging-port`, `--headless=new`), pointed browser-harness at
its CDP WebSocket via `BU_CDP_WS`, and additionally routed it through this environment's
outbound proxy (`--proxy-server`, `--ignore-certificate-errors` for the proxy's own
intercepting cert) — none of that is documented in jev-ultrafast's README, all of it was
necessary to get real network access.

## The actual result

**Every one of the three tested allowlisted domains returned a Cloudflare bot-check page
instead of real content:**

| URL | What loaded |
|---|---|
| `https://gmgn.ai/` | "Attention Required! \| Cloudflare" — hard block |
| `https://dexscreener.com/solana` | "Just a moment..." — interactive verification |
| `https://www.geckoterminal.com/solana/pools` | "Just a moment..." — verification, retried 6× over 18s with zero change |

The GeckoTerminal case was retried specifically to rule out a transient, auto-resolving
challenge (some Cloudflare checks clear themselves after a few seconds of JS execution).
It did not clear in 18 seconds of waiting — that rules out "just needed more time" and points
at the automated-browser fingerprint itself failing the check (headless flags, the
intercepting proxy's TLS fingerprint, or the proxy's shared egress IP reputation — not
distinguished further; distinguishing them would mean engineering around the block, which
this spike does not do and was not asked to do).

**On the one real decision the agent got to make** (gmgn.ai, `BLOCKED` at 98% confidence,
choosing correctly between only `scroll_down` and `wait` given a Cloudflare block page with
no real content) — jev-ultrafast's own reasoning was exactly right. It did not hallucinate
success on a page that had none. That's a genuine point in its favor, just not the point this
spike was measuring.

## What this actually answers

**Not "can jev-ultrafast read a table" — the spike never got far enough to test that.**
What it answers is a level up from the original question: **from this network position
(this environment's proxy egress), headless automated browsing cannot reach any of the three
tested fallback targets at all**, regardless of which engine drives it. This is not a
jev-ultrafast-specific finding. Base `browser-use` — the engine SPEC.md actually names — would
hit the identical Cloudflare challenge from the identical fingerprint, because the block
happens before either library's action-selection logic ever runs.

**This is a bigger problem for Hydra's PulseChain/Robinhood Chain fallback-hunter design
than "which browser-automation library" was ever going to be.** If the real deployment
environment's egress also trips these checks — plausible for any shared cloud/proxy IP,
not unique to this sandbox — the entire `browser.pulse_dex` / `browser.gmgn_ui` /
`browser.robinhood_dex` hunter category (SPEC.md §4.2) may be unreachable regardless of
engine choice, until solved at the network layer (a residential proxy pool, or a different
approach entirely) rather than the automation-library layer this proposal was evaluating.

**Do not read "not yet solved" as "solved the other way."** This result does not recommend
building Cloudflare-evasion tooling (fingerprint spoofing, residential proxy rotation, CAPTCHA
solving) to get past this. That would be a materially different, more adversarial posture than
"read-only hunting via allowlisted public pages," and is a decision for you, not something
to build toward on the strength of a blocked spike.

## Recommendation

1. **Don't decide the jev-ultrafast-vs-browser-use question from this result** — neither was
   actually tested against real page content. The question that needs answering first is
   whether the real deployment network can reach these sites headlessly at all, from
   wherever Hydra will actually run (not this evaluation sandbox).
2. If you want to re-run this from an environment more representative of where Hydra would
   actually be hosted, the exact repro is: `services/browser-hunter/spikes/jev_ultrafast_spike.py`
   plus the Chrome-launch and `BU_CDP_WS` steps above (not yet folded into the spike script
   itself, since they're specific to this sandbox's proxy setup, not to jev-ultrafast).
3. If Cloudflare blocking turns out to be the deployment reality too, that's a finding for
   the structural-edge-inventory-style ledger this project already keeps elsewhere (tradecc) —
   worth recording as a real constraint on the hunt-plane design, not silently working around.
